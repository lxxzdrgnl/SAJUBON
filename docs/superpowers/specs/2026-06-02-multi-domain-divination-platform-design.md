# 멀티 도메인 점술 플랫폼 — 설계 문서

> 작성일: 2026-06-02
> 상태: 초안 (사용자 리뷰 대기)
> 토픽: moonmarin8 데이터셋을 활용한 도메인 플러그인 아키텍처 + 하이브리드 상담 Agent

---

## 1. 배경과 목표

### 1.1 계기
외부 운세 서비스 `moonmarin8`의 MariaDB 덤프(48MB, 226 테이블, ~20만 행)를 확보했다.
단순 사주 데이터가 아니라 **동·서양 점술 전 분야를 망라한 콘텐츠 DB**이며, 상당수가
SajuGuri의 "헤드라인 결론형(Headline-Driven)" 문체와 동일하다.

목표는 **"이 데이터를 전부 활용하는 Agent"** 를 만드는 것이다. 이는 현재의 단일 사주
파이프라인을 **여러 점술 도메인을 플러그인으로 확장 가능한 플랫폼**으로 진화시키는 것을
의미한다.

### 1.2 핵심 판단 — 보강 vs 재설계
덤프의 도메인을 **"현 만세력 엔진으로 계산되는가"** 기준으로 가르면 방향이 결정된다.

| 그룹 | 도메인 | 입력 | 처리 | 결론 |
|---|---|---|---|---|
| **Group 1** | 성격·재물·직업·건강·학업·자녀·연애/궁합·시기흐름·신살/십성/용신 풀이·오늘의 운세 | 생년월일시+성별 (동일) | 현 만세력 엔진 (동일) | **순수 보강으로 충분** |
| **Group 2** | 자미두수 / 주역·토정비결·육임·타로 / 작명 / 태몽·꿈해몽 / 풍수 / 별자리·혈액형·MBTI·바이오리듬 | **제각각** (이름·꿈·질문·집방향 등) | **다른 엔진/룩업 또는 없음** | **재설계 필요** |

→ **결론: 순수 보강은 Group 1까지만 가능하다.** "다 활용하는 Agent"는 Group 2의 서로
다른 입력 계약(input contract)과 엔진 때문에 재설계가 필수다. 단, **버리는 재설계가 아니라
기존 engine/rag/writer를 재사용하는 "도메인 플러그인 아키텍처"로의 진화적 재설계**다.
기존 사주 파이프라인은 이 구조의 **첫 번째 플러그인**이 된다.

### 1.3 목표 (Goals)
- **모바일 우선 (mobile-first) — 최우선 원칙.** 모든 UI/응답 설계는 모바일 화면·터치·
  세로 스크롤을 기준으로 한다. **최종 목표는 앱 출시**다.
- 점술 도메인을 **플러그인 모듈**로 추가/관리하는 오케스트레이션 층 도입
- 기존 사주 파이프라인을 첫 도메인 모듈로 재정의 (동작 변경 없음)
- 덤프를 활용해 **기존 사주 지식·탭을 즉시 보강** (Phase 1)
- batch 리포트(구조적 뷰) + 상담 Agent(대화) **하이브리드** 제공
- Group 2 도메인을 순차적으로 플러그인 추가

> **모바일·앱이 백엔드에 주는 함의**: 응답 페이로드는 모바일에서 가볍고 점진적으로
> 렌더링 가능해야 한다(탭별 lazy load, 스트리밍). 도메인 모듈의 `WriterOutput`은
> 모바일 카드/탭 단위로 분할 소비 가능한 구조를 유지한다.

### 1.4 비목표 (Non-Goals)
- 덤프 원문을 그대로 RAG에 통째 인제스트하는 것 (품질·설계 훼손 — §4 참조)
- UI 최종안 확정 (§7에서 기본 방향만 제시, 변경 가능)
- 모든 Group 2 도메인을 한 번에 구현 (로드맵으로 단계화)
- 덤프 원본 `.sql` 파일을 저장소에 커밋 (보안 §8)

## 2. 데이터셋 인벤토리 (확정 사실)

### 2.1 계산·참조 테이블 (텍스트 아님 → 엔진/룩업용, RAG 부적합)
| 테이블 | 행수 | 내용 |
|---|---|---|
| `LunarToSolar` | 109,938 | 음↔양력 변환표 |
| `mansedata` / `manse_data` | 44,345 / 3,564 | 만세력(간지·절입) |
| `namedata` | 4,908 | 작명용 한자 사전(획수·오행·뜻) |
| `surioheng` | 276 | 작명 수리오행 |
| `tojung_gabja` | 60 | 토정비결 갑자 |
| `yukim_720` | 720 | 육임 720과 |
| `juyek_6hyo` | 64 | 주역 6효 |
| `toC_yongsin_01` | 120 | 용신 |

> 만세력·음양력 변환은 엔진이 이미 구현(`engine/calc/calendar_converter.py`,
> `solar_terms.py`) → **대부분 중복**. 교차검증 용도로만 활용. 작명용
> `namedata`/`surioheng`은 신규 기능의 룩업 소스로 가치 있음.

### 2.2 해석 텍스트 콘텐츠 (~170 테이블 → RAG/리포트 후보)
- **사주 분석 탭** (S 계열 대량): 성격/기질/적성, 재물/직업/학업, 건강, 자녀운, 계절/심리
- **궁합** (G·N 계열): 결혼후·바람기·미래배우자(얼굴/성격/직업), 섹스/속궁합, 오행·사상체질·감정케미, 관계별 조화(연인/친구/동업/직장/고부/승부), 혈액형
- **시기·운세 흐름**: 오늘의 운세(총운/애정/소망/사업/방위/금전 `S087~92`), 올해 운(`S106~109`), 일년신수(`S142,143`)
- **자미두수**: `J017~030` (子궁 자미 등 12궁 해설, 정통 고전 문체)
- **주역 64괘**: `J004~010`, 동전·단시점
- **태몽·꿈해몽**: `F007`(태몽), `F020`(꿈해몽 10,569행)
- **풍수**: 주택·대문·이사(`F011,12`, `F022`)
- **작명 격국**: `N002~005,15`
- **기타 점술**: 토정비결 괘사(`J036~044`), 타로(`T043,53`), 별자리, MBTI, 바이오리듬, 탄생석, 행운색·명당·띠

### 2.3 품질 평가 (설계에 직접 영향)
콘텐츠는 두 종류로 나뉜다:
1. **S/G/N/T 계열** — SajuGuri 문체와 판박이. **AI 생성물일 가능성이 높음.** 스타일은
   완벽하나, AI 생성 텍스트를 RAG 근거로 다시 AI에 먹이면 **순환 참조**라 "근거"로서의
   가치는 약하다. → **표현·톤 레퍼런스**로는 최상, "지식 근거"로는 신중.
2. **J 자미두수 / S045~056 등** — 정통 고전 문체. **진짜 명리 지식**에 가까워 RAG 근거
   자산으로 더 가치 있다.

→ 이 평가가 §4의 **2계층 RAG + 출처/신뢰도 태깅** 설계 근거다.

### 2.4 전체 활용 원칙 (Use-Everything)
**226개 테이블을 전부 활용한다. 버려지는 테이블은 없다.** 단 "한 컬렉션에 통째로
쏟기"가 아니라 **"전부 적재 + 도메인별 라우팅"**이다.

| 덤프 분류 | 목적지 | 비고 |
|---|---|---|
| 계산·참조 테이블 (§2.1) | engine / lookup | 신규 도메인 엔진·룩업 소스 (작명·주역·육임 등) |
| 해석 콘텐츠 ~170 테이블 (§2.2) | **Tier2 corpus 전부 인제스트** | 도메인별 컬렉션, 검색 대상 |
| 정통 고전 텍스트 (자미두수·고전 풀이) | Tier1 큐레이션 보강 | 엔진 태그 매칭 근거로 승격 |

> **`trust` 태그는 "저장 여부"가 아니라 "Writer 사용 방식"만 제어한다.** 모든 텍스트는
> 저장·검색되며, `ai_generated`는 표현/톤 참고로, `classical`은 사실 근거로 쓰인다.

## 3. 아키텍처

### 3.1 전체 구조
```
                  ┌──────────── Orchestrator Agent ────────────┐
  사용자 입력  ──→ │ (LangGraph) 의도·입력 분석 → 도메인 라우팅   │
  + 의도          │  · 누락 입력 대화로 수집 (이름·꿈·질문 등)    │
                  │  · 도메인 모듈을 tool/subgraph로 호출         │
                  └───────────────────┬─────────────────────────┘
                                      ▼  (모든 도메인이 동일 계약 준수)
   ┌──────────────┬──────────────┬──────────────┬──────────────────┐
   │ saju (기존)   │ 궁합          │ 자미두수      │ 작명/태몽/주역... │
   │ engine + RAG │ engine + RAG │ 新 engine+RAG │ lookup + RAG     │
   │ + writer     │ + writer     │ + writer      │ + writer         │
   └──────────────┴──────────────┴──────────────┴──────────────────┘
        ▲                                              │
        │ batch 리포트 (구조적 뷰)        대화 응답 ◀───┘
        └────────── 둘 다 동일한 도메인 모듈을 호출 ──────────┘
```

### 3.2 두 진입 경로 (하이브리드)
동일한 도메인 모듈을 **두 방식**으로 호출한다:
- **Batch 리포트 경로** (현 `run_saju_report` 패턴): 입력 완비 → 도메인 모듈 1회 실행 →
  완성 JSON 반환 → 프론트는 탭=뷰 전환. **CLAUDE.md의 "한 번에 생성" 원칙 유지.**
- **대화 경로** (현 `chat.py` LangGraph 패턴): Orchestrator Agent가 의도 파악 → 누락
  입력 수집 → 도메인 모듈을 tool로 호출 → 대화형 응답·후속 질문.

> 이 하이브리드의 토대는 이미 존재한다: `llm/pipelines/saju_report.py`(batch)와
> `llm/pipelines/chat.py`(LangGraph ReAct agent + guard). 재설계는 이 둘을 **도메인
> 플러그인을 소비하도록 일반화**하는 작업이다.

### 3.3 도메인 모듈 계약 (Domain Module Contract)
모든 도메인은 아래 인터페이스를 구현한다. (위치 제안: `domains/<name>/`)

```python
class DomainModule(Protocol):
    key: str                      # "saju" | "compatibility" | "jamidusu" | "naming" ...
    display_name: str             # "사주 분석"
    input_schema: type[BaseModel] # 이 도메인이 요구하는 입력 (생일 / 이름 / 꿈텍스트 / 질문 ...)
    rag_namespace: str            # ChromaDB 컬렉션 prefix (도메인별 격리)

    def compute(self, inp: InputModel) -> ComputeResult:
        """엔진 계산 또는 룩업. 엔진 없는 도메인은 입력을 그대로 통과."""

    def build_rag_context(self, computed: ComputeResult) -> dict:
        """결정론적 RAG 조립 (LLM 호출 없음). 기존 rag_builder 패턴."""

    async def write(self, computed, rag_ctx, concern) -> WriterOutput:
        """Writer LLM → 헤드라인 결론형 탭. 기존 writer 패턴."""
```

- **`compute`**: Group 1은 만세력 엔진, 자미두수는 신규 명반 엔진, 주역/타로는 괘 도출
  로직, 작명은 namedata 룩업, 태몽/풍수는 입력 통과(no-op).
- **`input_schema`**: Orchestrator가 이걸 보고 **무엇을 더 물어볼지** 결정한다 (대화 경로
  의 핵심).
- **`rag_namespace`**: 도메인별 ChromaDB 컬렉션 격리 (§4).

기존 사주 파이프라인은 이 계약을 만족하도록 얇게 래핑한다 (`SajuDomain`).

## 4. RAG 전략 — 2계층 + 출처 태깅

§2.3의 품질 편차 때문에 **기존 큐레이션 자산을 보호**하면서 덤프를 활용하는 2계층 구조를
쓴다.

### 4.1 Tier 1 — Curated (primary, 기존)
- 기존 컬렉션: `ilju, ten_gods, sin_sal, structure_patterns, dynamics, wuxing`
- **손으로 큐레이션한 구조화 JSON** (`embedding_context`/`engine_tags`/`interpretation_tags`/...)
- **엔진 결과와 태그 매칭**되는 핵심 자산 (`rag/search.py`의 `_match_by_tags`)
- **덤프를 그대로 넣지 않는다.** 대신 덤프를 참고해 **빈칸을 채운다**:
  - `ilju`: **이미 60갑자 완비(60개)** — 확장 불필요.
  - `sin_sal`: **RAG 9개 vs 엔진 계산 ~20개** → **갭 ~11개**(감수·고신·망신·문곡·반안·
    원진·월덕·육해·장성·태극·현침·홍염 등) 풀이를 채움. 덤프 신살 풀이(`S126` 천을귀인
    등)가 소스. **이것이 P1 최우선 보강.**
  - `ten_gods`/`structure_patterns`: 부족 항목 보강.

### 4.2 Tier 2 — Corpus (보조, 신규)
- 도메인별 신규 컬렉션: `corpus_saju, corpus_compatibility, corpus_jamidusu, ...`
- 덤프 텍스트를 **클렌징 후** 인제스트 (HTML 태그 `<BR>`, `<FONT c< body>` 제거, 인코딩 정규화)
- **메타데이터에 출처·신뢰도 태깅**:
  ```json
  {"source": "moonmarin8", "domain": "compatibility",
   "trust": "ai_generated" | "classical", "table": "G001", "express": "1"}
  ```
- Writer는 Tier 1(근거) + Tier 2(표현·톤·다양성)를 **구분해서** 사용.
  - `trust=classical` → 지식 근거로 활용 가능
  - `trust=ai_generated` → 표현/헤드라인 레퍼런스로만, 사실 근거로 인용 금지

### 4.3 임베딩
- 외부 API 통일 (사용자 결정). 기존 Gemini `embedding-001` 스택 유지.
- 보안 제약(§8): 덤프 파생 텍스트의 API 전송은 허용됨(사용자 확인).

## 5. 데이터 처리 파이프라인 (덤프 → 지식/코퍼스)

오프라인 ETL. 저장소 밖(`~/Downloads`) 원본을 읽어 가공물만 저장소에 남긴다.

```
.sql 덤프
   │  ① 파싱     : 테이블별 행 추출 (Python, 인코딩 utf8/utf8mb4)
   ▼
원시 레코드
   │  ② 클렌징   : HTML 태그·깨진 마크업 제거, 공백 정규화
   ▼
정제 텍스트
   │  ③ 분류     : 테이블 → 도메인 매핑 (§2 인벤토리 기반 룰)
   ▼
도메인별 레코드
   ├─→ ④a Tier 2 인제스트 : corpus_<domain> 컬렉션 (출처·신뢰도 태깅)
   └─→ ④b 큐레이션 보조    : 덤프 참고 → 기존 JSON 스키마 항목 작성
                              (LLM 보조 변환 + 사람 검수 게이트)
```

- **③ 분류**는 §2 인벤토리를 룰 테이블로 코드화한다 (테이블명 → domain, trust).
- **④b 큐레이션**: 덤프 텍스트를 기존 스키마(`embedding_context`/`engine_tags`...)로
  변환하는 작업. LLM 초안 → **사람 검수** 후 `rag/knowledge/*.json`에 반영. AI 생성
  의심 텍스트를 무비판적으로 근거화하지 않기 위한 게이트.

| `domains/` (신규) | 도메인 모듈 패키지. `base.py`(계약), `saju/`(기존 래핑), 이후 도메인 추가 |
| `llm/pipelines/` | `run_saju_report` → `run_domain_report(domain_key, inputs)` 일반화 |
| `llm/pipelines/chat.py` | Orchestrator로 확장 — 도메인 라우팅 + 입력 수집 노드 추가, 도메인 모듈을 tool로 등록 |
| `rag/db.py` | `COLLECTIONS`에 `corpus_*` 추가, namespace 헬퍼 |
| `rag/ingest.py` | Tier 2 코퍼스 인제스트 함수 추가 (출처·신뢰도 메타) |
| `rag/knowledge/*.json` | Tier 1 보강 (60갑자 일주, 신살 추가 등) |
| `scripts/etl/` (신규) | 덤프 파싱·클렌징·분류·인제스트 ETL |
| `engine/` | 신규 도메인용 엔진 추가 시에만 (자미두수 명반, 주역 괘 도출 등) |
| `schemas/` | 도메인별 입력 스키마, `WriterOutput` 재사용/확장 |
| `.gitignore` | 덤프 `.sql` 및 중간 산출물 제외 (보안) |

## 7. UI 방향 — PC·모바일 둘 다 구현 (모바일 우선)

> **PC UI와 모바일 UI를 모두 구현한다(반응형).** 단 설계·검증 우선순위는 모바일이며,
> 최종 목표는 앱 출시다. 공통 컴포넌트·상태를 공유하되 레이아웃은 분기한다.

### 7.0 PC(데스크탑) 레이아웃
- **2단 구성**: 좌측 만세력 표 앵커(고정), 우측 사주 탭 리포트. 상담은 우측 사이드
  패널 또는 모달로 상시 호출.
- 넓은 화면을 활용해 탭 리포트·궁합을 한눈에. 채팅도 사이드에 동시 표시 가능.

### 7.1 모바일 레이아웃
- **하단 탭 바**: `내 사주` · `상담` · `궁합` · `더보기`(작명·태몽·운세 등 도메인 허브)
- **만세력 표 = context 앵커**: "내 사주" 화면 상단의 **접이식(collapsible) 카드**.
  가로 스크롤 가능한 4기둥 표. 아래로 사주 탭 리포트가 세로로 이어짐.
- **사주 탭 리포트**: 모바일 탭 칩(가로 스크롤) → 탭별 **lazy load**. 한 번에 다 그리지
  않고 점진 렌더링 (§1.3 모바일 함의).
- **상담**: 풀스크린 채팅 화면 (모바일 네이티브 채팅 패턴).

### 7.2 채팅 UX (GPT 스타일)
- **`+` 첨부 버튼**: 채팅 입력창 좌측 `+` → **프로필 링크/첨부** 시트. 저장된 사주
  프로필(또는 방금 만든 명식)을 대화에 첨부하면, 그 명식이 Orchestrator의 컨텍스트로
  주입된다. (예: "이 프로필로 올해 운세 봐줘")
- 첨부된 프로필은 채팅 상단에 **칩**으로 표시, 제거·교체 가능.
- Group 2 도메인 입력(이름·꿈·질문 등)도 `+` 또는 대화 흐름으로 수집.

### 7.3 비로그인(게스트) + localStorage 최근 프로필
- **비로그인 상태에서도 핵심 기능 사용 가능** (앱 첫 진입 마찰 최소화).
- 날짜 입력 시 **localStorage에 저장된 최근 입력 프로필**을 자동완성/바로가기로 노출.
  - 저장 항목: 이름(별칭)·생년월일시·성별·달력종류 (개인정보 최소화, 클라이언트 보관)
  - 로그인 시 localStorage 프로필을 서버 계정으로 **병합(merge) 마이그레이션** 제안.
- 백엔드 함의: 리포트/상담 API는 **프로필 ID 없이 원시 생년월일 입력만으로도** 동작해야
  함 (이미 `run_saju_report`가 birth 인자를 직접 받음 — 게스트 호환).

근거: 기존 자산(만세력 표, `chat.py`, `AI 상담하기` 버튼)을 모바일 형태로 발전시키며,
앱 전환·게스트 사용·GPT식 친숙한 채팅 UX를 모두 만족한다.

### 7.4 앱 패키징 (방향만, 확정은 추후)
현 프론트는 Nuxt.js. 앱화 후보: **PWA**(가장 가벼움) → **Capacitor**(Nuxt 웹뷰 래핑,
스토어 출시 가능) → 네이티브(최후). 모바일 우선 웹을 먼저 완성하고 Capacitor로 감싸는
경로를 1순위 후보로 둔다. (별도 검토 — §12)

## 8. 보안 제약

- **원본 `.sql` 덤프를 공개 위치(공개 git repo·공유 데이터셋)에 올리지 않는다.**
  현재 `~/Downloads`에 있어 저장소 밖 — 안전. 저장소 내부로 복사 시 `.gitignore` 필수.
- 덤프 **파생 텍스트의 외부 API(임베딩·LLM) 전송은 허용** (사용자 확인).
- ETL 중간 산출물(정제 텍스트 덤프 등)도 저장소에 커밋하지 않는다.

## 9. 에러 처리

- **도메인 입력 누락**: Orchestrator가 `input_schema` 검증 → 대화로 재요청 (배치 경로는 400).
- **RAG 빈 결과**: 기존 동작 유지 — 빈 컨텍스트로 Writer 진행 (`rag/db.py`가 빈 컬렉션 시 `[]`).
- **Writer 파싱 실패**: 기존 `_parse_with_recovery` 1회 재시도 유지.
- **ETL 클렌징 실패 레코드**: 스킵 + 로그, 인제스트 중단 없음.
- **신규 엔진(자미두수 등) 계산 실패**: 해당 도메인만 graceful degrade, 다른 도메인 영향 없음.

## 10. 테스트 전략

- **도메인 계약 준수**: 각 모듈이 `DomainModule` 프로토콜을 만족하는지 (compute/build_rag_context/write 시그니처·반환형).
- **ETL**: 클렌징 함수 단위 테스트 (HTML 제거·인코딩), 분류 룰 테이블 검증.
- **Tier 분리**: Writer가 `trust=ai_generated`를 사실 근거로 인용하지 않는지 (프롬프트·후처리 검증).
- **회귀**: 기존 사주 리포트 출력이 래핑 후에도 동일한지 (golden test).
- **Orchestrator 라우팅**: 의도→도메인 매핑, 입력 수집 흐름.

## 11. 단계별 로드맵

| Phase | 내용 | 산출물 |
|---|---|---|
| **P0 — 기반** | 도메인 모듈 계약(`domains/base.py`), 기존 사주를 `SajuDomain`으로 래핑(동작 불변), ETL 스캐폴드, `.gitignore` | 플랫폼 골격 + 회귀 통과 |

## 12. 미해결 / 리스크

- **자미두수 명반 엔진**: 만세력과 별개 계산 체계. 구현 난이도 큼 → P5로 분리, 별도 spec 권장.
- **주역 괘 도출 방식**: 시간 기반? 난수? 사용자 동전던지기 입력? P5에서 결정.
- **AI 생성 콘텐츠 비율**: 덤프 중 실제 AI 생성 비율 미확정. ETL 시 표본 검수로 `trust` 라벨 정확도 확보 필요.
- **큐레이션 비용**: Tier 1 보강은 사람 검수가 병목. LLM 초안 품질에 따라 속도 좌우.
- **PC·모바일 이중 UI 유지비**: 두 레이아웃을 구현·유지해야 함. 공통 컴포넌트/상태 공유로
  중복 최소화하되, 레이아웃 분기 지점을 명확히 둘 것.
- **앱 패키징 경로**: PWA vs Capacitor vs 네이티브 미확정(§7.4). 모바일 우선 웹 완성 후
  별도 검토. 푸시·결제·스토어 정책이 변수.
- **게스트→로그인 마이그레이션**: localStorage 프로필을 서버 계정으로 병합하는 충돌 처리
  (중복·덮어쓰기) 규칙 필요.
- **UI 확정**: §7은 기본 방향. 실제 프로토타입 후 재검토.
